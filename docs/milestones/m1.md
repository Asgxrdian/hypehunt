# M1 Specification — Accounts, Preferences & Profile

**Status: Awaiting founder approval — no implementation until ratified**
**Depends on:** M0 (complete). **Bible refs:** §1 (security), §5 (schema), §7 (app architecture), §9 (testing).

## 1. Goal

Let a person create an account, tell HyperHunt what kinds of games and platforms they like, securely save that information, and return later without losing it.

## 2. Scope

**In:** Welcome screen · email/password sign-up · email/password sign-in · forgot-password flow · genre preference picker · platform preference picker · "Skip for now" · profile screen · edit preferences · sign out · session persistence · RLS isolation proof.

**Out (explicitly):** Google Sign-In, Apple Sign-In, search, deals, wishlist, alerts, recommendations, avatars/photo upload, account deletion UI (pre-launch checklist item), deep links.

## 3. Decisions requiring founder sign-off

These three choices are embedded in this spec; approving the spec approves them.

**D1 — Email confirmation is OFF for M1.** Supabase can require users to click an email link before their account activates. That link needs mobile deep-link handling we haven't built. For M1 (no public users), we disable confirmation so sign-up is instant. Re-enabling it, with proper deep links, is added to the pre-launch checklist alongside credential rotation.

**D2 — Password reset uses a 6-digit code, not a link.** Supabase's reset email will be templated to contain a one-time code. Flow: user enters email → receives code → enters code + new password in the app. No deep links, no browser hand-off, fully testable now. (Same mechanism can later serve email confirmation.)

**D3 — Username is optional in M1.** Sign-up requires only email + password. The profile screen shows the email and offers an optional username field (3–24 chars, unique — the DB constraint already exists). Forcing username choice at sign-up adds friction and a "name taken" loop we don't need yet.

## 4. User flows

**First launch → account.** App opens to Welcome: logo, one line of copy, [Create account] and [Sign in]. Sign-up asks email + password (single field, show/hide toggle, live validation: valid email, min 8 chars). On success the DB trigger creates `profiles` + `user_preferences` rows automatically, the session is stored on-device, and the user lands in Taste Setup.

**Taste Setup (onboarding).** Step 1 of 2 — "What do you like to play?": chip grid of ~19 genres, tap to toggle, zero-to-many allowed, [Continue] and [Skip for now]. Step 2 of 2 — "Where do you play?": chip grid of 5 platforms, same controls, [Finish] and [Skip for now]. Skip at any point goes straight to the home shell; nothing blocks. Selections save to `user_preferences` on finish (single update, not per-tap).

**Returning user.** App start checks the persisted session (handled by supabase_flutter's local storage). Valid session → straight to home shell, no login wall. No session → Welcome. Expired-but-refreshable sessions refresh silently.

**Sign in.** Email + password. Failure shows one honest inline message ("Email or password is incorrect") — never revealing which was wrong, and never a raw error code. Links to Forgot password.

**Forgot password.** Enter email → "If an account exists, a code is on its way" (same message whether or not the account exists — prevents account-enumeration probing) → enter code + new password → signed in.

**Profile & preferences.** Profile tab shows email, optional username (editable), genre chips, platform chips, [Edit preferences] (reuses the Taste Setup chip grids, pre-filled), and [Sign out]. Sign out clears the session and returns to Welcome.

**Routing rule.** go_router redirect: unauthenticated users can only reach Welcome/auth screens; authenticated users can't navigate back to auth screens. Onboarding is offered once after sign-up but is never a locked gate (deep respect for D-skip).

## 6. Database interactions

**No schema changes.** M1 runs entirely on M0's migration.

Sign-up hits Supabase Auth; the existing `on_auth_user_created` trigger inserts the `profiles` and `user_preferences` rows server-side, so the client never creates them. Preference reads/writes are single-row `select`/`update` on `user_preferences` by the signed-in user's id, flowing through the publishable key and therefore through RLS — the owner-only policy is the enforcement, not client code. Username updates touch `profiles.username`; a duplicate raises the DB's unique violation, surfaced as "That username is taken." One Supabase dashboard change accompanies D1/D2: email confirmation toggled off, and the recovery email template edited to show the OTP code.

## 7. Testing plan

**Unit (pure Dart):** validators (email shapes, password length), auth controller state transitions (loading→data, loading→error on bad credentials) and profile controller save logic — repositories mocked, no network.

**Widget:** sign-up form validation states; sign-in error rendering; taste setup — chips toggle, skip navigates without writing, finish emits exactly the selected slugs; profile renders the four UI states.

**RLS isolation (the M1 exit test).** A scripted integration test using two dedicated test accounts (test-a@, test-b@ on the live project):
1. Sign in as A, write distinctive preferences.
2. Sign in as B; attempt to `select` A's `user_preferences` and `update` A's rows by id.
3. Assert reads return zero rows and writes affect zero rows / error.
4. Repeat in the other direction, and assert each user *can* read and write their own rows.
Run manually for M1 sign-off with output pasted into the PR; wiring it into CI with GitHub-secret credentials is a fast-follow.

**Manual smoke:** kill and relaunch the app while signed in → lands on home shell without login (session persistence proof). Sign out → relaunch → Welcome.

## 8. Definition of done

M1 is done when all of the following are true on `main` with green CI:
1. A new user can go from install → account → taste setup → home shell in under a minute, entirely in-app.
2. Skip works at every onboarding step and the app is fully usable with empty preferences.
3. Preferences and username survive sign-out/sign-in and app restart.
4. Forgot-password with the code flow works end-to-end on a real inbox.
5. The RLS isolation test passes in both directions, output recorded in the PR.
6. Every new screen implements loading/data/error/empty states; zero analyzer warnings.
7. No secrets in the diff; auth screens contain no third-party keys.
